- В таблице сессий хранятся текущие сессии. Но могут быть ситуации когда происходят какие-то изменения. 
- К примеру, изменения в рамках маршрутизации. Если до этого исходящий интерфейс был один, а после изменений в RT исходящий интерфейс стал другой, то сессия не дропнется, в случае если оба интерфейса принадлежат к одной и той же зоне. То же самое относится и к ассиметричной маршрутизации (исходящий один, входящий другой).
- Если интерфейсы находятся в разных зонах, то сессия сохраняться не будет.
- 
- Если изменения произошли в policy.

- В политике существует настройка **policy-rematch**. Это настройка заставляет перепроверить сессии при изменении политики.
- По умолчанию, при удалении политики, все сессии дропаются. При изменении action или критериев, то сессии продолжают работать.
- Если включен rematch, при удалении политики - сессии дропаются, при изменении action на deny или reject - сессии дропаются, при изменении критериев - сессии пересматриваются
- 
- У каждого firewall есть размер таблицы сессий, зависит от модели. 
- Когда таблица полна, то новые не создаются. 
- Есть default timeout:
- TCP - 30 min
- UDP - 1 min
- ICMP - 1 min
- Существуют агрессивные timeout
- ![](https://remnote-user-data.s3.amazonaws.com/Mn_Oc7tGk6CtPOAy8vTyJ51TxseJPFuZpkLRquAe9mww5rbJpNokMgFRKW4y5TEQdcOgPcOmMkEx9aW46HDwmGP1ivZyG1bG8sjSD70XxuTPrP1P_CaBH8tzUcGGANWt.png)
- Для TCP существуют проверки, что пакеты верные и в том порядке.
- SYN checking - проверяет, что первый пакет сессии SYN, затем SYN-ACK, а потом ACK. При ассиметричной маршрутизации это правило будет мешать, т.к. не пропустит пакеты. Можно отключить. 
- RST - checking
- Sequence number checking
- Initial TCP session timeout
- Всё это можно отключить
- Есть еще настройки для MSS
