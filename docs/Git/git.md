- # Установка Git
- Git - система контроля версий. Позволяет сохранять разные версии данных (файла, документа) и после просматривать эти изменения
- 
- sudo apt install git-all - установка git на Linux
- 
- git --version - проверка версии git
- 
- # Репозиторий
- Репозиторий - место хранения кода и других данных
- 
- Репозитории бывают:
    - Локальный - хранится локально на компьютере пользователя
    - Удаленный - хранится на хостинге git
- 
- Удаленный репозиторий необходим для дополнительного хранилища и как следствие для резервирования репозитория, а так же для общего доступа к репозиторию для других пользователей.
- 
- git init -  создать (инициализировать) локальный репозиторий. После чего создастся папка .git
- 
- Для связывания локального и удаленного репозитория используется команда git remote add origin [http://192.168.32.13/mvin/edu-git.git](http://192.168.32.13//mvin/edu-git.git), где
- git - программа git,
- remote - говорит о том, что будем работать с удаленным репозиторием,
- origin - название удаленного репозитория,
- [http://192.168.32.13/mvin/edu-git.git](http://192.168.32.13//mvin/edu-git.git) - адрес удаленного репозитория.
- 
- # Commit
- 
- Commit - фиксация, сохранение изменений, произведенных над файлом в репозитории.
- 
- Commit по сути состояние изменений файлов.
- 
- После внесения изменений в наши файлы, с ними ничего не происходит, они никак не отслеживаются и не комитятся.
- 
- Чтобы сделать коммит, нужно определить изменения каких файлов будут отслеживаться.
- 
- git add . -p -  команда для добавления в индекс для коммит, где git - команда git
- add - команда уточнение, что сейчас будем добавлять изменения в индекс
- . - добавляем рассматривание изменений в текущей папке и всех подпапках
- -p (patch) - позволяет посмотреть все изменения, которые были сделаны в репозитории в интерактивном формате
- 
- 
- После применения команды, git покажет изменения в каждом отдельном файле (это называется hunk - кусок). Можно увидеть, чего не станет, а что будет новое.
- 
- После чего git будет ждать нашего ответа, принимать это изменение или нет. Самые простые и понятные ответы: y/n (да или нет соот-но).
- 
- После ответа он перейдет на следующий файл (или кусок).
- 
- Получается мы контролируем, какие изменения мы добавляем, а какие нет.
- 
- Но коммит еще не создан.
- 
- Чтобы сделать коммит:
- 
- git commit - сделать коммит. После чего откроется текстовый редактор, чтобы ввести комментарий к коммиту. По сути комментарий описывает то, что было сделано
- 
- git status - команда показывает файлы, которые были изменены. При команда отображает, какие измененные файлы будут добавлены в коммит (командой git add), а какие нет.
- 
- git commit -m "Второй коммит" - позволяет сделать коммит более короткой командой. По сути флаг -m позволяет написать комментарий прямо в терминале.
- 
- git commit --allow-empty -m "Пустой коммит" - команда позволяет сделать пустой коммит. Для чего это надо мне пока не ясно, но видимо иногда может потребоваться.
- 
- git log - команда показывает список коммитов. В ней указан id коммита, пользователя, сделавшего коммит, дату и время и комментарий. Так же показывает ветку, в которую был сделан коммит.
- 
- git rm - удалить файл с добавлением изменения в индекс коммита.
- 
- git checkout - удалить изменения в файле, который еще не закоммичен. То есть отменить те действия, которые делались над файлом. По сути является rollback 0 в терминологии Juniper.
- 
- git checkout . - удалить изменения в файлах, которые находятся в конкретной папке и её подпапках. То есть отменить те действия, которые делались над файлами. По сути является rollback 0 в терминологии Juniper. Так же вместо точки (.) можно использовать название конкретной папки.
- 
- git reset 1.txt - удалить изменение из индекса. Как я понял, мы удалили файл из кандидатов на коммит. Ну а дальше чтобы отменить изменения используем git checkout

- # Branch
- Branch - ветка в репозитории git (в доке это указатели на коммиты). Это одно из ветвлений развития репозитория. Другая ветка это по сути клон основной ветки, с того момента, с какого коммита её создали. Она может быть полезна, когда внедряется новая функциональность, и чтобы не ломать существующий функционал. Ветки друг от друга изолированы, и изменения в одной ветке не влияют на другую. При создании репозитория создается одна основная ветка - master.
- 
- git branch - посмотреть все ветки (* отображается активная)
- 
- git branch -a - посмотреть все ветки (вместе с удаленными)
- 
- git branch -r - посмотреть только удаленные ветки
- 
- git branch newBranch - создание новой ветки newBranch
- 
- git branch checkout newBranch - переключиться на другую ветку (в данном случае newBranch)
- 
- git checkout -b develop - создать ветку develop и сразу же перейти в неё
-

- git checkout HEAD^ - переход на коммит, который является на один шаг предыдущим от текущего коммита.
- 
- Здесь пожалуй надо пояснить
- **checkout **- команда, которая позволяет "гулять" по репозиторию, как по веткам, так и по коммитам.
- **HEAD** - это указатель на последний коммит текущей ветки. HEAD указывает, что мы будем работать с этим коммитом.
- **^ **показывает на один шаг назад. Учитывая, что эта директива стоит около HEAD, значит, на один коммит назад от HEAD
- 
- git checkout HEAD^^ - переход на коммит, который является на два шага предыдущим от текущего коммита.
- 
- git checkout master - вернуться обратно в последний коммит ветки master

- git branch develop - создаем новую ветку develop
- git checkout develop - переходим в эту ветку

- # Работа с удаленным репозиторием
- Чтобы работать с удаленным репозиторием (пушить в него изменения и стягивать с него) для начала нужно связать локальный репозиторий с удаленным.
- 
- Как уже ранее писалось, делается это следующей командой:
- 
- git remote add origin [http://192.168.32.13/mvin/slurm_git.git](http://192.168.32.13/mvin/slurm_git.git)
- 
- Как я понял, origin, это название краткий псевдоним (alias) для длинного URL. По сути получается сопоставление origin и [http://192.168.32.13/mvin/slurm_git.git](http://192.168.32.13/mvin/slurm_git.git). Чтобы не писать длинный URL, можно просто писать origin. Но при этом псевдоним может быть любым. То есть название его можно менять.
- 
- После того как мы сделаем какие-то изменения в наших файлах:
- echo 111 > 1.txt
- git add .
- git commit -m "Изменения в файле 1.txt"
- 
- и дальше захотим запушить эти изменения на удаленный репозиторий у нас это может не получится. Всё потому что git еще не знает с какой веткой на удаленном репозитории соотносить нашу локальную ветку, в котором мы сейчас находится.
- 
- Ну и он нам предложит команду, которой это можно решить:
- 
- git push --set-upstream origin master
- 
- Расшифруем:
- --set-upstream origin master - устанавливает связь между удаленным репозиторием (URL находится в origin) ветки master и  нашим локальным репозиторием, в котором находимся.
- 
- Если мы сделали отображение ветки в консоли, то можем увидеть, где сейчас находится
    - esperance@esperance ~/edu_git(master) [12:37]:
- или сделать git branch.
- 
- git remote -v - показывает соответствие между названием удаленного репозитория и его URL.
- 
- git push - отправить изменения на удаленный репозиторий
- 
- Для того, чтобы привязать локальный репозиторий к другому удаленному репозиторию, выполняем ту же команду, что и ранее. Только теперь меняем название.
- 
- git remote add new_slurm_git [http://192.168.32.13/mvin/new_slurm_git.git](http://192.168.32.13/mvin/new_slurm_git.git)
- 
- git remote remove gitlab_repo - удалить связь между локальным репозиторием и удаленным репозиторием gitlab_repo
- 
- Если мы хотим сделать новую ветку в локальном репозитории и потом запушить её на удаленный репозиторий (на удаленном репозитории новой ветки нет), то делаем следующие действия:
- 
- git branch develop - создаем новую ветку
- git checkout develop - переходим в новую ветку
- git push - пытаемся запушить и получаем сообщение об ошибке
- git push --set-upstream origin develop - применяем предлагаемую нам команду. После чего установится связь между локальной ветки
- 
- В git есть возможность использовать тэги. С помощью тэгов можно отмечать версии продукта.
- 
- git tag - показывает все тэги в репозитории
- 
- git tag -a 0.1 -m "my first tag" - создать тэг (-a - аннотация тэга, -m - комментарий)
- 
- git push --tags - отправить в удалённый репозиторий только тэги
- 
- И на странице репозитория в хранилище (GitHub/Gitlab) появится тэг.
- 
- В git так же существует возможность забирать изменения из удаленного репозитория и немедленно обновлять эти изменения.
- 
- git pull - забрать изменения с удаленного репозитория и немедленно их обновить в локальном
- 
- Так же можно забирать с удаленного репозитория отдельные ветки.
- 
- git fetch origin develop - стянуть с удаленного репозитория origin ветку develop (не забываем что origin, это сопоставление краткого имени и URL).
- 
- git fetch origin develop:myOwnDevelop - стянуть с удаленного репозитория origin ветку develop (не забываем что origin, это сопоставление краткого имени и URL) и присвоить ей другое имя (в данном случае myOwnDevelop)
- 
- Ранее мы использовали две команды git pull и git fetch.
- Они выполняют одно и то же, но имеют разный подтекст.
- 
- git pull - стягивает все изменения из удаленного репозитория и сразу же обновляет все изменения. Если к примеру на удаленном репозитории есть файл 1.txt в котором записано 111, а в локальном репозитории есть такой же файл 1.txt, но в котором записано 11, то после применения git pull, в локальном у нас станет 111.
- 
- git fetch - стягивает все изменения из удаленного репозитория, но сразу же они не применяются. Есть возможность посмотреть какие есть изменения. И видимо при желании применить их или отменить.
